## 一、推荐系统基础

### 题目1：推荐系统的完整链路是什么？你的项目如何实现？

**参考答案**：
推荐系统典型链路分四阶段：
1. **召回（Recall）**：从海量商品中初筛出几百-几千个候选，强调速度
2. **粗排（Coarse Ranking）**：对召回结果快速打分，缩减到几百个
3. **精排（Fine Ranking）**：用复杂模型精准打分，排序出 Top-K
4. **重排（Re-ranking）**：考虑多样性、新颖性、业务规则做最终调整

我的项目实现了**召回层**：
- 使用 LightGCN 学习 user/item 嵌入
- 将 item_embedding 入库 Qdrant
- 用 user_embedding 在 Qdrant 做向量检索，召回 Top-K 相似商品

**知识点**：
- 召回 vs 排序的核心区别：召回重速度和覆盖度，排序重精度
- 多路召回（协同过滤、向量召回、热门召回、内容召回）
- 漏斗结构：每层缩减一个数量级

**延伸追问**：
- Q：为什么不实现精排？
- A：精排需要更多特征工程和更复杂模型（如 DIN/DIEN），简历项目聚焦召回链路。生产中精排常用 GBDT+LR 或深度模型（如 DeepFM）。

### 题目2：协同过滤有哪些类型？LightGCN 属于哪一种？

**参考答案**：
协同过滤主要分三类：
1. **基于用户（UserCF）**：找相似用户，推荐他们喜欢的东西
2. **基于物品（ItemCF）**：找相似物品，推荐给喜欢类似物品的用户
3. **基于模型（ModelCF）**：用机器学习模型学习用户/物品嵌入
   - 矩阵分解（MF/BPR）
   - 深度学习（NeuMF、Wide&Deep）
   - 图神经网络（GCN、LightGCN、GraphSAGE）

LightGCN 属于**基于模型的图神经网络协同过滤**，它将用户-物品交互建模为二部图，通过图卷积传播信息。

**知识点**：
- UserCF 适合新闻场景（兴趣时效性强）
- ItemCF 适合电商场景（物品关系稳定）
- 图模型能捕获高阶协同信号（user-item-user-item 链路）

**延伸追问**：
- Q：LightGCN 相比传统矩阵分解的优势？
- A：传统 MF 只建模一阶交互（直接 user-item），LightGCN 通过多层图卷积捕获高阶协同信号（二阶、三阶邻居），推荐更精准。

## 二、LightGCN 模型

### 题目3：LightGCN 的核心创新是什么？为什么比传统 GCN 更适合推荐？

**参考答案**：
LightGCN 的核心创新是**"轻量化"**——去除传统 GCN 中的两个组件：
1. **去除特征变换矩阵（W）**：不学习权重参数
2. **去除非线性激活（ReLU）**：不应用激活函数

只保留**图卷积聚合**和**层间求和**。

**为什么更适合推荐**：
- 推荐场景下用户/物品只有 ID（没有丰富特征），特征变换无意义
- 实验证明在推荐任务上，传统 GCN 的特征变换和非线性反而会**过拟合**，降低性能
- LightGCN 参数量大幅减少，训练速度提升 5-10 倍

**知识点**：
- 传统 GCN：`H = σ(D^(-1/2) A D^(-1/2) H W)`
- LightGCN：`H = D^(-1/2) A D^(-1/2) H`（去除 W 和 σ）
- 层聚合：最终嵌入 = 各层嵌入的均值

**延伸追问**：
- Q：LightGCN 的层数怎么选？
- A：论文实验表明 3 层效果最好。层数过少（1-2层）捕获不到高阶信号；层数过多（4+层）会导致过平滑（over-smoothing），所有节点嵌入趋同。

### 题目4：LightGCN 的损失函数是什么？为什么用它？

**参考答案**：
LightGCN 使用 **BPR（Bayesian Personalized Ranking）损失**：

```
L = -Σ ln σ(pos_score - neg_score)
```

其中：
- `pos_score` = 用户向量 · 正样本物品向量（用户交互过的物品）
- `neg_score` = 用户向量 · 负样本物品向量（用户未交互的物品）

**为什么用 BPR**：
1. **优化排序而非评分**：推荐系统关心的是相对排序（A 比 B 更值得推荐），而不是绝对分数
2. **适合隐式反馈**：天池数据只有行为（pv/buy）没有评分，BPR 专为隐式反馈设计
3. **理论优雅**：源自贝叶斯概率，最大化后验概率

**知识点**：
- BPR 假设：用户对正样本的偏好 > 负样本
- 负采样：每个正样本配1个负样本（LightGCN 论文配置）
- 与交叉熵损失对比：交叉熵适合多分类，BPR 适合 pairwise 排序

**延伸追问**：
- Q：BPR 和 Hinge Loss 的区别？
- A：Hinge Loss：`max(0, margin - (pos - neg))`，需要调 margin；BPR 用 sigmoid 软化，无需 margin 参数，梯度更平滑。

### 题目5：解释 LightGCN 的归一化邻接矩阵公式

**参考答案**：
LightGCN 使用**对称归一化拉普拉斯矩阵**：

```
L = D^(-1/2) * A * D^(-1/2)
```

其中：
- **A**：大图邻接矩阵 `[[0, R], [R^T, 0]]`，R 是 user-item 交互矩阵
- **D**：度矩阵（对角阵），`D_ii = Σj A_ij`

**为什么这样归一化**：
1. **D^(-1/2) 左乘**：按行的度归一化，降低高度数节点（热门商品）的影响
2. **D^(-1/2) 右乘**：按列的度归一化，对称处理
3. **避免热门商品主导**：不归一化的话，热门商品会被过度推荐

**代码实现**（见 [graph_builder.py:103](file:///d:/ec-agent-rec/data_processing/graph_builder.py)）：
```python
d_inv_sqrt = np.power(row_sum, -0.5)
d_mat_inv_sqrt = sp.diags(d_inv_sqrt)
norm_adj = d_mat_inv_sqrt.dot(adj_matrix).dot(d_mat_inv_sqrt)
```

**知识点**：
- 对称归一化 vs 随机游走归一化（D^(-1) A）
- GCN 论文使用对称归一化
- 邻接矩阵构建：将 user-item 矩阵扩展为 (N+M) × (N+M) 的大图

**延伸追问**：
- Q：为什么用大图而不是分别处理 user 和 item？
- A：大图让信息可以在 user-item 之间双向传播。一次图卷积后，user 嵌入聚合了 item 信息，item 嵌入聚合了 user 信息，实现协同过滤。

### 题目6：LightGCN 的层聚合为什么用均值而不是拼接？

**参考答案**：
LightGCN 采用**层均值聚合**：

```
e_u = (e_u^(0) + e_u^(1) + e_u^(2) + e_u^(3)) / 4
```

而非拼接 `concat(e_u^(0), e_u^(1), e_u^(2), e_u^(3))`。

**原因**：
1. **防止过平滑**：拼接会让深层特征主导，加剧过平滑问题
2. **维度一致**：均值保持嵌入维度不变，便于内积计算
3. **实验验证**：论文消融实验显示均值优于拼接和加权求和
4. **参数更少**：拼接需要额外的变换矩阵降维

**知识点**：
- 过平滑（Over-smoothing）：GCN 层数过多，所有节点嵌入趋同
- 残差连接：另一种缓解过平滑的方法
- 层聚合策略：均值、求和、拼接、注意力加权

**延伸追问**：
- Q：如何判断模型是否过平滑？
- A：监控训练中各层嵌入的相似度（如 cosine），如果深层嵌入间平均相似度 > 0.9，说明过平滑。也可以看验证集指标，层数增加但指标下降是典型信号。

## 三、图神经网络

### 题目7：什么是二部图？推荐系统中如何构建？

**参考答案**：
**二部图（Bipartite Graph）**：图中节点分为两个不相交的集合，边只存在于两个集合之间，集合内部无边。

推荐系统中的二部图：
- **集合1**：所有用户 U = {u1, u2, ..., un}
- **集合2**：所有商品 I = {i1, i2, ..., im}
- **边**：用户与商品的交互（浏览/购买）

**构建方式**（见 [graph_builder.py:75](file:///d:/ec-agent-rec/data_processing/graph_builder.py)）：
```python
# 邻接矩阵 R: (num_users, num_items)
# R[u, i] = 1 表示用户 u 与商品 i 有交互

# 扩展为大图 A: (num_users + num_items, num_users + num_items)
A = [[0,    R],
     [R^T,  0]]
```

**知识点**：
- 二部图特性：无奇数长度环
- 邻接矩阵的稀疏性（用 CSR 格式存储）
- 度矩阵：行的度 = 用户交互数，列的度 = 商品流行度

**延伸追问**：
- Q：为什么不在 user-user 或 item-item 之间直接建边？
- A：1) 数据中没有显式的用户关系；2) 二部图结构简单，便于图卷积传播；3) 高阶 user-user 关系可以通过多层 GCN 隐式捕获（user-item-user）。

### 题目8：图卷积（Graph Convolution）的物理含义是什么？

**参考答案**：
图卷积的物理含义是**信息聚合**：每个节点从邻居那里"收集"信息，更新自己的表示。

在推荐系统中：
- **第0层**：用户嵌入 = 用户初始 Embedding
- **第1层**：用户嵌入 = 聚合其交互过的商品的嵌入
- **第2层**：用户嵌入 = 聚合"与其交互商品相似的用户的嵌入"
- **第3层**：捕获更远的高阶协同信号

**公式**：
```
e_u^(l+1) = Σ_{i ∈ N(u)} (1 / sqrt(|N(u)| * |N(i)|)) * e_i^(l)
```

**直观理解**：
- 1 层 GCN = "我买过的商品代表了什么"
- 2 层 GCN = "和我买过相似商品的人还买了什么"
- 3 层 GCN = 更高阶的协同信号

**知识点**：
- 一阶邻居、二阶邻居、高阶邻居
- 信息传播 vs 信息聚合
- GCN vs GraphSAGE vs GAT 的聚合方式差异

## 四、向量检索

### 题目9：为什么用 Qdrant 而不是 FAISS？

**参考答案**：
| 维度 | Qdrant | FAISS |
|------|--------|-------|
| 定位 | 向量数据库 | 向量检索库 |
| 数据管理 | 支持 payload、过滤、更新 | 仅向量检索 |
| 持久化 | 自带磁盘持久化 | 需自己实现 |
| 动态更新 | 支持在线增删 | 需重建索引 |
| API | REST + Python SDK | Python/C++ |
| 过滤检索 | 原生支持 | 需额外实现 |
| 部署 | Docker/云服务 | 库集成 |

**选择 Qdrant 的原因**：
1. **支持 payload 过滤**：可以按商品分类、价格等过滤后再检索
2. **动态更新**：商品库变化时无需重建索引
3. **生产友好**：自带持久化、监控、API
4. **简历亮点**：云原生向量数据库，更贴近生产架构

**知识点**：
- 向量索引算法：HNSW、IVF、PQ
- Qdrant 默认使用 HNSW（Hierarchical Navigable Small World）
- FAISS 适合静态数据的大规模批量检索

**延伸追问**：
- Q：HNSW 的原理？
- A：分层小世界图，上层稀疏快速导航，下层密集精确搜索。查询时从顶层开始贪心搜索，逐层下沉，兼顾速度和精度。

### 题目10：向量检索的距离度量有哪些？你的项目为什么选 Dot？

**参考答案**：
常见距离度量：
1. **Cosine 余弦相似度**：`cos(u,v) = (u·v) / (|u||v|)`，归一化后计算
2. **Dot 内积**：`dot(u,v) = Σ u_i * v_i`，不归一化
3. **Euclid 欧氏距离**：`d(u,v) = sqrt(Σ(u_i - v_i)^2)`

**项目选择 Dot 的原因**：
- LightGCN 训练时用**内积**计算推荐分数：`score = user_emb · item_emb`
- 如果用 Cosine，会丢失向量模长信息（模长可能编码了用户活跃度/商品流行度）
- 用 Dot 保证**训练目标与召回目标一致**

**最初的设计错误**：
- 初版用 Cosine，被审查后发现不一致，已改为 Dot
- 这体现了"训练- Serving 一致性"的重要性

**知识点**：
- 度量一致性原则：训练打分函数 = 召回打分函数
- 归一化的影响：Cosine 适合文本相似度，Dot 适合推荐打分
- 内积的几何含义：投影长度

**延伸追问**：
- Q：什么场景下用 Cosine 更合适？
- A：文本/图像语义相似度（向量模长无意义时）。如 RAG 中的文档检索，用 Cosine 是因为 Embedding 模型训练时通常做了归一化。

## 五、缓存设计

### 题目11：Redis 缓存策略是什么？如何保证数据一致性？

**参考答案**：
项目采用**TTL + 主动失效**双策略：

**TTL 策略**：
- 召回结果缓存 1 小时（3600秒）
- 简单有效，无需额外触发
- 适合不活跃用户

**主动失效**（改进建议）：
- 用户产生新购买行为时，主动清除该用户的召回缓存
- 保证新行为能立即反映在推荐中

**缓存键设计**：
```
key = recall:user:{user_id}:top{top_k}
value = [item_id_1, item_id_2, ...] (JSON)
```

**缓存击穿/穿透/雪崩防护**：
- **击穿**：热门 key 失效瞬间大量请求打到 Qdrant → 加互斥锁
- **穿透**：查询不存在的 user_id → 缓存空值
- **雪崩**：大量 key 同时失效 → TTL 加随机抖动

**知识点**：
- Cache Aside / Write Through / Write Back 模式
- LRU、LFU 淘汰策略
- 缓存预热、降级

**延伸追问**：
- Q：缓存命中率怎么提升？
- A：1) 热门用户主动预热；2) 调大 TTL；3) 相似用户共享缓存（user clustering）；4) 对召回结果做分桶缓存。

## 六、Agent 设计

### 题目12：电商 Agent 的工作流程是什么？

**参考答案**：
项目 Agent 流程（见 [ecommerce_agent.py:27](file:///d:/ec-agent-rec/agent/ecommerce_agent.py)）：

```
1. 接收用户输入 (user_id, user_message)
2. 意图识别（welcome/recommend/explain/category）
3. 推荐引擎召回：
   a. 检查 Redis 缓存 → 命中直接返回
   b. 未命中 → 从 user_embedding 获取用户向量

6. 解析回复（自然语言 + item_id 列表）
7. 返回给用户
```

**关键设计**：
- 意图识别决定 Prompt 模板选择
- 缓存层减轻向量库压力
- Mock LLM 保证无 API Key 也能演示

**知识点**：
- Agent 核心要素：感知 → 决策 → 行动
- ReAct 框架（Reasoning + Acting）
- Tool Use（工具调用）：Agent 调用推荐引擎这个"工具"

**延伸追问**：
- Q：如何让 Agent 支持多轮对话？
- A：维护对话历史，每轮将历史消息拼接到 Prompt 中。注意 Token 限制，可用滑动窗口或摘要压缩。

### 题目15：训练/验证/测试集如何划分？有什么坑？

**参考答案**：
项目采用**按用户划分**（见 [dataset.py:65](file:///d:/ec-agent-rec/data_processing/dataset.py)）：
- 每个用户的交互按 8:1:1 划分到 train/val/test
- 保证每个用户在三个集合中都有数据

**划分代码逻辑**：
```python
for user_idx in range(num_users):
    pos_items = list(adj_matrix[user_idx].indices)
    np.random.shuffle(pos_items)
    n_train = int(n * 0.8)
    n_val = int(n * 0.1)
    # train: pos_items[:n_train]
    # val: pos_items[n_train:n_train+n_val]
    # test: pos_items[n_train+n_val:]
```

**常见坑**：
1. **数据泄漏**：训练集和测试集有重复交互 → 必须按 user_id 划分，且去重
2. **冷启动用户**：交互数 < 3 的用户无法划分 → 特殊处理（全进训练集）
3. **时序泄漏**：随机划分可能把未来行为放进训练 → 应按时间划分（但天池数据时间跨度短）
4. **评估时未排除训练集**：推荐时要把训练集商品过滤掉，否则会"推荐用户已买的"

**项目中的处理**：
- 评估器 [evaluator.py:55](file:///d:/ec-agent-rec/model/evaluator.py) 正确排除了训练集商品

- 留出法、K折交叉验证、时序划分

## 八、评估指标

### 题目16：Recall@K 和 NDCG@K 的区别？什么场景用哪个？

**参考答案**：
**Recall@K（召回率）**：
```
Recall@K = |推荐TopK ∩ 真实交互| / |真实交互|
```
- 衡量"真实感兴趣的物品有多少被推荐出来了"
- 不考虑排序位置
- 适合：信息检索、覆盖度优先场景

**NDCG@K（归一化折损累计增益）**：
```
DCG@K = Σ (rel_i / log2(i+1))  # rel_i 是位置i的相关性
NDCG@K = DCG@K / IDCG@K  # IDCG 是理想排序的 DCG
```
- 衡量"推荐排序的质量"
- 排在前面的物品权重更大（log 折损）
- 适合：排序质量优先场景（如电商首页推荐）

**项目中的应用**：
```python
# evaluator.py
for k in [20, 50]:
    recall = hits / len(test_items)
    ndcg = self._calculate_ndcg(topk, test_items)
```

**知识点**：
- Precision@K、MAP、MRR
- 折损函数：1/log2(i+1)
- IDCG：理想情况下的 DCG，用于归一化

**延伸追问**：
- Q：为什么推荐系统常用 Recall@K 而不是 Precision@K？
- A：推荐系统物品池巨大（百万级），用户真实兴趣只是冰山一角。Precision@K 会因为分母 K 小而虚高，Recall@K 更能反映"是否覆盖了用户兴趣"。

### 题目17：项目为什么设计降级机制？如何实现？

**参考答案**：
**为什么设计降级**：

**实现方式**（见 [qdrant_client.py:34](file:///d:/ec-agent-rec/vector_store/qdrant_client.py)）：
```python
def _init_client(self):
    try:
        from qdrant_client import QdrantClient
        self.client = QdrantClient(host=self.host, port=self.port)
    except ImportError:
        logger.warning("qdrant_client 未安装，使用本地内存模式")
        self._local_mode = True
        self.client = None
    except Exception as e:
        logger.warning(f"Qdrant 连接失败，使用本地内存模式: {e}")
```

- Circuit Breaker 模式
- 健康检查与自动恢复

### 题目19：如果用户量增长到 1 亿，你的设计有哪些瓶颈？

**参考答案**：
**瓶颈1：user_embedding 内存加载**
- 1 亿用户 × 64 维 × 4 字节 = 25.6GB，单机无法加载
- **解决**：user_embedding 入 Redis/Qdrant，按需检索

**瓶颈2：Qdrant 单节点**
- 1 亿商品向量 + 检索 QPS 上万 → 单节点扛不住
- **解决**：Qdrant 集群分片（按 item_id hash）

**瓶颈3：图构建内存**
- 1 亿边的大图，邻接矩阵即使用 CSR 也要数 GB
- **解决**：分布式图计算（DGL、GraphLearn）

**瓶颈4：训练速度**
- 单卡 GPU 训练 1 亿交互的 LightGCN 需要数小时
- **解决**：多 GPU 数据并行、采样训练（GraphSAGE 思路）

**知识点**：
- 垂直扩展 vs 水平扩展
- 数据分片、副本
- 采样训练（邻居采样）

### 题目20：如何评估这个推荐系统的线上效果？

**参考答案**：
**离线指标**（已实现）：
- Recall@20、NDCG@20、Precision@20
- 局限：无法反映真实用户体验

**线上指标**：
1. **点击率 CTR** = 点击数 / 曝光数
2. **转化率 CVR** = 购买数 / 点击数
3. **GMV** = 推荐带来的成交金额
4. **人均推荐点击数** = 总点击 / 活跃用户数
5. **推荐覆盖率** = 被推荐过的商品数 / 总商品数
6. **多样性** = 推荐列表的平均相似度（越低越好）

**A/B 测试**：
- 对照组：旧推荐策略
- 实验组：新策略（LightGCN）
- 流量分桶：按 user_id hash 分桶
- 指标显著性：t 检验、p < 0.05

**知识点**：
- 离线指标与线上指标的差距（ Offline-Online Gap）
- 幸存者偏差、选择偏差
- A/B 测试的统计显著性

**延伸追问**：
- Q：如果 A/B 测试结果不显著怎么办？
- A：1) 检查样本量是否足够（功效分析）；2) 分群分析（新老用户、不同品类）；3) 检查指标定义是否合理；4) 考虑长期效果（ novelty effect）。
